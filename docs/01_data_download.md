# Stage 0A — تنزيل بيانات TCIA

## لماذا التنزيل حسب SeriesInstanceUID؟

واجهة `getImage` في NBIA تُرجع ZIP لسلسلة محددة. استخدام UID صريح يجعل التجربة قابلة لإعادة الإنتاج ويمنع تغيّر مجموعة البيانات عندما تتغير نتائج البحث أو ترتيبها.

## ملف الإدخال

الـ CSV ليس مجرد قائمة روابط؛ إنه جزء من بروتوكول التجربة. `case_id` اسم محلي غير طبي، و`role` تصريح بشري مبدئي لا يُستنتج خلسة من اسم السلسلة. يجب مراجعة الدور بعد الفهرسة.

## دورة حياة الملف

1. يكتب التنزيل إلى `<uid>.zip.part`.
2. عند وجود الملف يرسل `Range: bytes=N-`.
3. لا يتم append إلا إذا رد الخادم بـ `206 Partial Content`.
4. إذا عاد `200 OK`، يبدأ الملف من الصفر حتى لا نلصق ZIP كاملًا فوق جزء قديم.
5. يُفحص ZIP بواسطة `testzip()`.
6. بعد النجاح فقط يُعاد اسمه ذريًا إلى `.zip`.
7. يُحسب SHA-256 ويكتب سجل JSON.

## الحدود المعروفة

- الاستكمال يعتمد على دعم الخادم لـ Range؛ عند غيابه نعيد السلسلة بأمان.
- التوازي يقع بين السلاسل، لأن NBIA يعيد ZIP واحدًا للسلسلة.
- الكود لا يكتشف السلاسل تلقائيًا بعد؛ الاختيار العلمي للـ pilot خطوة بشرية مقصودة في هذه المرحلة.
- عدم وجود API key في الكود متعمد لأن مجموعات TCIA العامة لا تحتاج سرًا.

## تشخيص الأخطاء

- `No enabled series`: كل الأسطر `enabled=false`.
- `invalid DICOM SeriesInstanceUID`: القيمة ليست UID رقميًا منقّطًا أو أطول من 64 حرفًا.
- `Corrupt ZIP member`: التنزيل اكتمل شكليًا لكنه تالف؛ يُعاد بعد حذف `.zip.part` إذا لزم.
- HTTP 4xx: راجع UID؛ لا تغيّر `role` لحل مشكلة رابط.
